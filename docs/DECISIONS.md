# Server-checked shared member password — Roger's decision, 2026-11-04

Roger chose **«Server checks shared pw»**. This supersedes the 2026-09-02 decision to retain the browser-only gate and the SB-02/03 limitation recorded above. Members keep the same password and German gate screen. The old `VITE_GATE_PASSWORD_HASH` was compiled into the public bundle and is not a server credential.

Implementation choice: a server-side constant-time password-hash comparison, a shared database-backed IP rate limit, then a native Supabase Auth session for a dedicated shared member identity. The server generates and consumes an admin magic-link token itself; it sends no email and leaves public email/phone/signup/anonymous Auth disabled. Supabase owns signing and rotating refresh tokens. Access tokens expire after 15 minutes. Session storage keeps the former tab lifetime, and multiple devices remain allowed. Future personal Auth accounts can receive the same server-managed membership without replacing the policies.

PR #37 landed during this work and is retained: the existing 30-day absolute / 7-day inactive session targets are applied only where the Supabase plan offers them, with an explicit release warning otherwise. On the currently recorded **Free** plan, native refresh sessions have **no absolute or inactivity cutoff**; refresh rotation, the 15-minute access-token expiry and server membership revocation still apply. Closing the tab discards its browser-held refresh token, but does not revoke a copied token at the server. This is a documented platform limitation, not a claim of a 30-day server limit on Free. No plan upgrade or custom refresh service is introduced.

One migration moves the 14-table and four-RPC inventory to authenticated members with the existing column restrictions. Membership is checked against the Auth user's server-managed metadata, keyed by `auth.uid()`, rather than client-editable metadata. Public phone upload moves to a narrow edge handler accepting only a member-created, pending, unexpired 128-bit QR token and a single bounded receipt photo. Guest payments are member records, not a public guest sign-in flow. Receipt Storage and extraction also require membership.

Release preparation reuses the existing GitHub secret **by name only**, passing it to the settings step as `MEMBER_PASSWORD_HASH`, never to Vite. The settings step provisions the dedicated Auth identity and Supabase function secrets through the existing Management API mechanism and existing release-context checks. Staging goes first through Deploy; production remains Roger's manual promotion. This task makes no deployment, production or hosting request.

The server permits **10 password attempts per IP per 15-minute UTC window**, plus **60 per hour across the project**, using the existing atomic service-only `bump_extract_rate` RPC. Both good and bad attempts count; backend failure refuses sign-in. IP counter keys are HMAC digests, and the rightmost forwarded hop is used rather than caller-prepended values. The global cap also bounds guesses if gateway forwarding changes. There is no public mail form or existing CAPTCHA to reuse. Requests are bounded to 2 KiB/512 password characters, responses are `no-store`, and secrets/Auth responses are not logged.

The shared account is Roger's explicit exception to the general no-shared-accounts default. Its Auth password is a random unused server-generated credential; members never see or use it. An admin-generated, single-use link token is consumed immediately on the server with `verifyOtp`; no link or OTP is returned or mailed. Account id/email and server-managed membership are verified before issuance. Native Auth supports the later personal-login path without a custom JWT signing key or refresh service. See [generateLink](https://supabase.com/docs/reference/javascript/auth-admin-generatelink), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp), and [native sessions and rotation](https://supabase.com/docs/guides/auth/sessions). Access expiry is enforced by Supabase and additionally by the RLS membership predicate; removing the server membership flag immediately refuses table access even for an otherwise unexpired JWT. The frontend re-locks and clears query data on sign-out/expiry. A normal sign-out invalidates refresh tokens; an already issued access JWT otherwise lasts at most 15 minutes.

A phone holder can validate its own 128-bit token and upload one JPEG (10 MiB maximum) to `phone-uploads/<token>/photo.jpg`, only while that exact session is pending and unexpired. ## Amendment after the independent review of PR #38 (2026-11-04)

The review found the design sound but the release unsafe. Changed, superseding the paragraphs above where they differ:

The project-wide budget counts only WRONG passwords (60 per hour) and is read before comparing, so once spent no attempt is compared. Right passwords, malformed requests and preflights never spend it; one address can spend at most 40 of it per hour. The caller address is `cf-connecting-ip` when it holds a valid public address (Cloudflare overwrites it), else the rightmost `X-Forwarded-For` entry; with neither, there is no per-address bucket and only the global budgets apply, so a shared gateway address can never lock every member out (re-review F1, 2026-11-04). One helper, `supabase/functions/_shared/client-ip.ts`, now used by both `member-session` and `extract-expense`. The gate shows distinct messages for 429 and 503.
- **Tests.** A staging E2E posts the real shared password (Actions secret `MEMBER_GATE_PASSWORD`) to `member-session` and uses the returned session; production and staging releases stop before the upload unless a wrong password gets 401. Test processes receive the staging service key `BB_SVC_KEY`, never the org-wide `SUPABASE_ACCESS_TOKEN`.
- **Session limits in hours.** `sessions_timebox` 720 and `sessions_inactivity_timeout` 168 (the Management API reads hours, SR-AUTH-06); `configure-auth.mjs` refuses values outside 1..8760. Free-plan gating unchanged: on Free, refresh tokens do not expire, so a password change needs the admin global sign-out in the runbook.
